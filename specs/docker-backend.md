# Dockerized Local API Backend — Spec

## Objective

Package the Bach Path Python backend (`services/local-api` plus the
`wsi-fungal-segmentation` inference pipeline) as a single Linux Docker image so it
runs identically on any machine with Docker, eliminating the native-dependency
drift that currently makes the app "work on my machine but not in the lab"
(OpenSlide, libvips, Pillow, pinned Python 3.12/3.13, and CUDA torch wheels).

The Electron desktop UI continues to run natively on the host and talks to the
containerized backend over `http://127.0.0.1:8765`. On launch the desktop app
starts the backend container; on quit it stops it — replacing today's Python
subprocess spawn. The same image must also be runnable headless via
`docker compose up` for non-Electron/server users.

Target user (now): the lab Windows machine with an NVIDIA GPU. Target user
(future): anyone who wants to run Bach Path, via a publicly pullable image.

Success looks like: a lab operator installs Docker Desktop, launches the desktop
app, and import/inference work on the GPU with no Python, venv, OpenSlide, or
CUDA setup — and existing slides/runs/database from a prior native install are
still present.

## Requirements

Must-haves are numbered M#; explicitly-deferred nice-to-haves are listed under
"Deferred".

### Image contents and build

1. A `Dockerfile` (committed under the repo, e.g. `services/local-api/Dockerfile`
   or repo root) builds a **Linux image** containing:
   - The `services/local-api` application and its `requirements.txt` dependencies.
   - The `wsi-fungal-segmentation` inference code and its inference dependencies.
   - Native runtime libraries installed via the OS package manager: OpenSlide and
     libvips (so `openslide-python` and `pyvips` import and work).
   - A CUDA-enabled PyTorch matching the project's pin (cu124 / torch 2.6.0,
     torchvision 0.21.0) installed from the CUDA wheel index, **not** a `+cpu`
     build.
2. The base image provides a CUDA 12.x runtime compatible with cu124 wheels
   (e.g. an `nvidia/cuda:12.4.*-runtime` or `pytorch/pytorch` CUDA image). The
   image must run on a host whose NVIDIA driver supports CUDA 12.4.
3. Inside the image, the API and the inference subprocess share **one** Python
   environment. `INFERENCE_PYTHON` defaults to the container's own interpreter
   (the API must successfully spawn the inference subprocess inside the
   container). There are no `.venv` directories inside the image.
4. The current deploy model is **baked into the image** at a known path (e.g.
   `/app/models/deploy-fungus.pth.gz`) so inference works out of the box with no
   extra setup. Model discovery inside the container resolves to that path by
   default.
5. The image contains **no secrets and no patient/slide data**. The API key is
   injected at runtime (see M11). Build is reproducible from committed files only.

### Runtime: volumes, ports, environment

6. A persistent **app-data** location is bind-mounted into the container for
   `APP_DATA_DIR` (slides, `app.db`, `inference_runs`, `training_runs`,
   `tiles_cache`) and a separate mount for `APP_LOG_DIR`. When launched by
   Electron these bind to the existing host paths
   (`userData/api-data` and `userData/api-logs`) so data from a prior native
   install persists and survives image updates.
7. A single **slides inbox** host folder is bind-mounted read-only into the
   container at a fixed path (e.g. `/import`), and
   `APP_IMPORT_ALLOWED_ROOTS` is set to that in-container path so slides placed in
   the inbox can be imported. Imports copy the source into managed storage under
   `APP_DATA_DIR/slides` (existing `copy_into_managed_storage` behavior),
   unchanged.
8. An optional **models** host folder may be bind-mounted over the baked-in model
   path; if present and it contains a valid deploy weight (`.pth.gz` / `.pt.gz`),
   it overrides the baked-in model without rebuilding the image.
9. The container publishes the API on the host loopback only:
   `127.0.0.1:8765 -> 8765`. It must not be reachable on a non-loopback host
   interface by default.
10. The container runs with GPU access (`--gpus all` / compose `deploy.resources`
    device reservation). `APP_INFERENCE_DEVICE=auto` resolves to CUDA inside the
    container when the GPU is visible, and falls back to CPU when it is not, with
    a clear log line indicating which device was selected.
11. The API key is generated by the host (Electron, as today) and passed to the
    container via `-e APP_API_KEY=...`. `APP_ALLOW_QUERY_API_KEY=true` and
    `APP_CORS_ALLOW_FILE_ORIGIN=true` are set for the desktop launch, matching the
    current subprocess environment.

### Electron lifecycle integration

12. The Electron main process (`apps/desktop/index.js`) starts the backend by
    running the container (`docker run ...`) instead of spawning Python, and stops
    it (`docker stop`/container removal) on `window-all-closed` / `before-quit`.
    The existing `/health` readiness wait (`waitForHealth`) is reused before the
    window loads.
13. Electron references a **specific image tag** (a pinned, tested version — not
    `latest`). It pulls that tag if it is not already present locally before
    running.
14. If Docker is not installed, not running, or the image cannot be pulled,
    Electron surfaces a clear, actionable error (e.g. "Docker Desktop is required
    and must be running") instead of failing silently. The app does not crash.
15. Container start is idempotent: a stale/previous Bach Path backend container
    (same fixed name) is detected and reused or replaced rather than causing a
    port/name conflict.

### Delivery

16. A committed `docker-compose.yml` runs the same image headless with the volumes
    and environment from M6–M11, so a user can run `docker compose up` and reach
    the API at `127.0.0.1:8765` without the Electron app.
17. The image is publishable to **Docker Hub** under a public repository name
    (e.g. `bachpath/bach-path-api`). The build-and-push procedure (tagging with a
    semantic version and `latest`, `docker push`) is documented.
18. The `README.md` is updated with: Docker/WSL2/NVIDIA Container Toolkit
    prerequisites, how to run via Electron, how to run via compose, the inbox and
    models mount conventions, and the build+push steps. Native (non-Docker) setup
    instructions may remain as a development fallback but are no longer the
    primary path.

### Deferred (nice-to-haves, explicitly out of scope for this build)

- GitHub Actions CI workflow that builds and pushes on version tags.
- Multi-arch images (`linux/amd64` + `linux/arm64`) via `buildx`.
- GHCR mirror of the Docker Hub image.
- Image digest pinning (vs. tag pinning) in the Electron app.
- Containerizing the training/evaluate/export pipeline.
- Containerizing the Electron GUI itself.

## Constraints

- **Backend only.** The Electron GUI and the training pipeline are out of scope;
  do not containerize them.
- **Platform:** primary host is Windows 11 + NVIDIA GPU, using Docker Desktop with
  the WSL2 backend and the NVIDIA Container Toolkit for GPU passthrough. The image
  itself is Linux.
- **GPU is amd64/NVIDIA only.** Any future arm64/Mac image is CPU-only by
  necessity; do not claim GPU support there.
- **Compatibility:** do not change the API contract, ports, auth model, import
  semantics (copy-into-managed-storage), settings env var names, or the desktop
  renderer's API client. Existing `userData/api-data` databases and slides must
  keep working after the switch (no migration/data loss).
- **Security/privacy:** loopback-only exposure by default; no secrets or
  slide/patient data baked into the image; the inbox is mounted read-only; API key
  injected at runtime. Confirm the baked-in model's license permits public
  redistribution before publishing the image publicly.
- **Pinning over floating:** the desktop app must reference a fixed image
  tag/version, never `latest`, so app and backend ship as a known-good pair.
- **Build inputs:** reproducible from committed repo files; the build must not
  depend on a developer's local venvs or machine state.

## Edge Cases

- **Docker not installed / daemon not running:** Electron shows an actionable
  error and does not crash or hang (M14).
- **No NVIDIA GPU or toolkit missing on host:** container still starts; inference
  runs on CPU with a clear log line; whole-slide runs may be very slow but must
  not fail for lack of GPU (M10).
- **Host NVIDIA driver too old for CUDA 12.4:** GPU init fails inside the
  container; the backend must fall back to CPU (or surface a clear error) rather
  than crash on import.
- **Port 8765 already in use on host:** start fails with a clear message; the
  configured `apiPort` is honored if changed (existing config path).
- **Stale container from a previous run** (same fixed name) still present:
  reused or removed cleanly without a name/port conflict (M15).
- **Slide outside the mounted inbox:** import is rejected by
  `APP_IMPORT_ALLOWED_ROOTS` (expected), and the UI/API returns the existing
  "disallowed slide path" error rather than a confusing container path error.
- **Empty or missing models mount:** falls back to the baked-in model; inference
  still works (M4/M8).
- **Missing/invalid override model in the mounted models folder:** the existing
  "No deploy model found" behavior applies; baked-in model is used if the mount
  has no valid weight.
- **Image tag absent locally and pull fails (offline/auth):** Electron reports a
  clear pull error (M13/M14); no silent fallback to an untested image.
- **Prior native install's `api-data`** bind-mounted in: the containerized API
  opens the existing SQLite DB and slides without migration errors or data loss.
- **Inference subprocess inside the container:** the API-spawned inference process
  resolves `INFERENCE_PYTHON` to the container interpreter and runs; output-size
  adaptive-mask coarsening behavior is unchanged.

## Definition of Done

A reviewer can verify each item:

1. `docker build` of the committed Dockerfile produces an image with no manual
   steps beyond documented build args.
2. In a shell inside the built image, `python -c "import openslide, pyvips, torch;
   print(torch.__version__, torch.version.cuda)"` succeeds and prints a CUDA
   (non-`+cpu`) torch build.
3. Running the container on the lab machine with `--gpus all`, then
   `python -c "import torch; print(torch.cuda.is_available())"` inside it prints
   `True`.
4. With the container running (Electron-launched or `docker compose up`),
   `GET http://127.0.0.1:8765/health` returns 2xx.
5. Placing a `.svs`/`.tif` slide in the mounted inbox folder and importing it via
   the running app/API succeeds; the slide appears in the gallery and a copy
   exists under the app-data `slides` directory.
6. Running inference on an imported slide completes using CUDA (confirmed by a
   device log line) and overlays render in the viewer.
7. With no models folder mounted, inference uses the baked-in model and succeeds
   ("No deploy model found" does not occur).
8. Mounting a models folder containing a different valid deploy weight causes that
   weight to be used instead of the baked-in one (verifiable in run metadata/logs).
9. Launching the Electron desktop app starts the backend container automatically,
   the window loads after `/health` passes, and quitting the app stops/removes the
   container (verifiable via `docker ps`).
10. Launching with Docker Desktop stopped produces a clear in-app error message
    and the app does not crash.
11. Pointing the app-data bind mount at a pre-existing native install's
    `api-data` directory shows the previously imported slides and prior inference
    runs with no data loss or migration error.
12. The image is built, tagged with a semantic version and `latest`, and pushed to
    the public Docker Hub repository; a clean machine can `docker pull` it and run
    it via the committed `docker-compose.yml` to a healthy `/health`.
13. The API key is supplied only at runtime; `docker history`/image inspection
    shows no `APP_API_KEY`, slide data, or other secrets baked into any layer.
14. The container binds only to `127.0.0.1:8765`; it is not reachable on the host's
    LAN IP by default.
15. `README.md` documents prerequisites (Docker Desktop, WSL2, NVIDIA Container
    Toolkit), the Electron run path, the `docker compose` path, the inbox/models
    mount conventions, and the build+push procedure; following it on a clean
    machine reproduces a working backend.
